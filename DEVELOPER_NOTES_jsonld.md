# JSON-LD generation rules

## Purpose and scope

Use this note when adding or updating Schema.org JSON-LD for Pivtorak.Studio content. It documents the current architecture and safe content-level conventions; it does not authorize redesigning shared schema infrastructure. JSON-LD is not generated universally from Front Matter.

## Current architecture

- `layouts/_partials/docs/html-head.html` is included by `layouts/baseof.html`. It adds the active canonical link from Hugo's `.Permalink` and calls `layouts/_partials/schema.html`. The legacy Front Matter `canonical` param does not control that link; preserve it only when extending an established content family that already carries it, keeping it aligned with the rendered permalink. It is not a substitute for Hugo URL configuration.
- `layouts/_partials/schema.html` emits one `@graph` containing the central `Person`, `Organization`, and `WebSite` only on the English homepage. Their data comes from `data/seo/author.yaml` and `data/seo/organization.yaml`. IDs are `https://pivtorak.studio/en/#person`, `https://pivtorak.studio/en/#organization`, and `https://pivtorak.studio/en/#website`.
- Use `{{< schema-author-reference >}}` and `{{< schema-organization-reference >}}` to reference the central entities when a content block needs them. Do not define a second incomplete copy of those entities.
- Section-list shortcodes generate `ItemList` entries from actual selected pages. Keep the visible list and JSON-LD generated by the matching helper; never hand-maintain another list or count. See `DEVELOPER_NOTES_section_lists_jsonld.md`.
- Several pages have hand-authored JSON-LD immediately after Front Matter. The active head does not automatically turn arbitrary Front Matter into an Article, Artwork, or CollectionPage graph. Follow the page family's actual implementation and avoid adding a second conflicting graph.
- Hugo links translated pages through matching paths/base filenames or, where that structure does not fit, the built-in shared `translationKey`. That association is separate from JSON-LD identity: translated pages still need their own localized page URLs and language values, while shared entity IDs remain stable.

## Page types and content relationships

Choose types by what the page actually is; Schema.org types are descriptive vocabulary, not a claim of Google rich-result eligibility.

| Page/content | Project convention |
|---|---|
| Site homepage and shared identity | `WebSite`, `Person`, `Organization` are centrally defined in the English homepage graph. Reference the same IDs. |
| Informational landing page or collection | `CollectionPage` is used by the Timeline and the Events series landing page. Add `mainEntity` such as an `ItemList` or `CreativeWorkSeries` only when that entity is real and represented by the page. |
| Series | `CreativeWorkSeries` can describe a genuine series of published works. The Events landing page currently places it as `mainEntity`; give its entity a stable ID across translations only when translated pages refer to the same series. Do not use series type for a generic list or invent `hasPart` items. |
| Individual written analysis/article | `Article` is a suitable Schema.org type for an actual article. Existing individual pages do not receive an Article schema automatically; only add a block when the task calls for it and enough accurate content metadata is available. Do not use `NewsArticle` merely because an article discusses a recent event. |
| Individual visual artwork | Use `VisualArtwork` only when the page's principal subject is an artwork. An editorial illustration used as a page thumbnail does not make the page itself a VisualArtwork. Use accurate artwork properties (e.g. artform, medium, artist, dateCreated) only when known. |
| Section landing list | Use the existing generated `ItemList` implementation. Its `ListItem` names, positions, URLs and count must equal the rendered visible list. |
| Timeline | Existing page uses `CollectionPage` with a chronological `ItemList` as `mainEntity`, and `isPartOf`, author/publisher, image, topics and breadcrumb. It also references a different Website ID and local Person/Organization definitions than the central graph; do not copy those identities into new content. This is an existing consistency gap. |

Breadcrumb JSON-LD is present in `layouts/_partials/breadcrumb.html`, but current head invokes `schema.html`, not that partial. Confirm actual rendered output before assuming breadcrumbs are active.

## Properties and values

- Use exactly `"@context": "https://schema.org"` and a valid Schema.org `@type`.
- A page's `url` should be its actual language-specific Hugo permalink. `@id` identifies the described entity/page: use the page URL (or a deliberate fragment such as `#webpage` / `#series`) consistently. Do not source these values from the legacy `canonical` Front Matter param; check them against `.Permalink`. Stable series entity IDs should be shared across translated views of the same series; page IDs and URLs remain language-specific.
- Set `inLanguage` to the correct BCP 47 language tag (`uk`, `en`, `pt-PT`, or `ru` only for the disabled-language content). Do not use display label `UA` as the language code.
- Localize `name`, `headline`, `description`, `keywords`, and image captions. Values should agree with the corresponding page Front Matter and visible content.
- `datePublished` and `dateModified` should be real ISO 8601 values reflecting publication and modification. Preserve the intended offset when known. Do not copy an event date into a publication date without evidence.
- Resolve relative image paths to absolute URLs in JSON-LD. The image must exist and represent the page/work; do not confuse its alt text with a caption.
- Use central author and publisher references where appropriate. Do not invent authorship, publisher, `sameAs`, awards, dates, taxonomy entities, or relationships. `isPartOf`, `hasPart`, `mainEntity`, `creator`, and `publisher` must describe true relationships.
- Schema.org vocabulary does not make every property mandatory. Google eligibility rules are separate, change over time, and apply only to supported search features; do not promise a rich result from valid Schema.org JSON-LD.

## Embedding and formatting

For a content-embedded block, put the JSON-LD script after the closing Front Matter delimiter. Preserve exactly one blank line between the closing `---` and `<script type="application/ld+json">`. Keep the script as valid JSON except for established Hugo shortcode expressions that render to JSON values; use double quotes for JSON strings and escape embedded quotation marks. Do not wrap JSON in Markdown fences.

Example shape only (not a universal page template):

```html
<script type="application/ld+json">
{
  "@context": "https://schema.org",
  "@type": "CollectionPage",
  "@id": "https://pivtorak.studio/en/example/",
  "url": "https://pivtorak.studio/en/example/",
  "name": "Localized page name",
  "inLanguage": "en"
}
</script>
```

If an existing list shortcode is the source of an embedded JSON value, retain the established shortcode and its exact placement rather than hardcoding its result.

## Validation checklist

1. Confirm the actual page type, current language path, and existing schema for its family.
2. Confirm Front Matter and visible page values agree with JSON-LD; verify every URL, entity ID, image and referenced work exists.
3. Check translation pairs: localized page IDs/URLs and language values differ correctly; shared person, publisher, website and series IDs remain stable.
4. Check JSON syntax after Hugo shortcodes have rendered. Build Hugo and inspect the generated HTML; ensure there is no duplicate/conflicting entity definition and no malformed JSON caused by shortcode output.
5. For section lists, compare visible items against generated `ItemList` names, positions, URLs, and count. For Timeline, check actual visual-archive items and chronology.
6. Use Schema.org validation for vocabulary/graph issues and Google's Rich Results Test only for Google-supported eligibility; neither substitutes for checking site content or guarantees search display. Google distinguishes its feature eligibility policies from Schema.org vocabulary and does not guarantee a rich result even for valid markup; see [Google's general structured data guidelines](https://developers.google.com/search/docs/appearance/structured-data/sd-policies) and [Article feature guidance](https://developers.google.com/search/docs/appearance/structured-data/article).

## Architecture gaps to keep visible

- The Timeline block uses `https://pivtorak.studio/#website`, while the active central Website ID is `https://pivtorak.studio/en/#website`; it also locally repeats Person and Organization rather than using the central IDs. This conflicts with `DEVELOPER_NOTES_schema_architecture.md`'s stable-ID rule.
- The Timeline hand-authored block has no explicit `hasPart` entries for visual archive works; the actual visual archive is generated separately. Do not fabricate a list to fill this gap.
- `layouts/_partials/seo.html` contains a second hard-coded Person block and calls `breadcrumbs_schema.html`, but it is not called by the active `html-head.html`; current live output should be checked before treating those definitions as active. `layouts/_partials/breadcrumb.html` also exists separately.
- Current sections use multiple JSON-LD styles and some pages' embedded blocks are generated from manual values. Treat them as examples to audit, not proof of a site-wide universal schema. If changing architecture, update schema partials, affected content, and `DEVELOPER_NOTES_schema_architecture.md` together.

# Robots.txt: Когда файл существует, но не работает | SEO Хитрости

_Файл был на месте. URL был правильным. Сервер его возвращал. И всё же — он не выполнял того, что должен делать `robots.txt`._

## Краткое резюме

> Файл `robots.txt` может существовать по правильному URL и при этом быть неправильным.
> 
> В нашем случае Hugo создавал `/robots.txt`, но получившийся файл имел размер около 34 КБ и содержал длинный список страниц сайта вместо директив для роботов. Расследование показало, что неожиданный результат был связан с поиском шаблона в Hugo и универсальным шаблоном `all.txt` в теме `hugo-book`.
> 
> Решение оказалось простым: создать явный шаблон `layouts/robots.txt`, а затем проверить результат по схеме **Source → Build → Live**.

## Вопрос

Что происходит, когда `robots.txt` существует по правильному URL, но его фактическое содержимое неправильное?

Именно этот вопрос стал отправной точкой расследования. После того как в конфигурации Hugo было подтверждено `enableRobotsTXT = true`, ожидаемый `/robots.txt` был сгенерирован — но его содержимое не соответствовало функциональному robots-файлу.

Проблема уже заключалась не в том, существует ли файл. Вопрос был в том, **что именно Hugo сгенерировал**.

## Почему это важно

Для технического файла вроде `robots.txt` недостаточно получить ответ HTTP 200 или просто убедиться, что файл существует.

Его содержимое должно выполнять предназначенную для него функцию. Если сгенерированный результат неожиданен, проверка только URL может скрыть настоящую проблему.

Поэтому в этом расследовании внимание было сосредоточено на сгенерированном содержимом, исходном шаблоне и пути от конфигурации Hugo до конечного файла.

**Мы не измеряли конкретного влияния на crawling, индексацию или позиции в поиске**, поэтому данное расследование не утверждает, что неправильный файл вызвал такие последствия.

## Проверка

Расследование началось с проверки рабочего URL:

```text
https://pivtorak.studio/robots.txt
```

Первая проверка показала:

```text
404 File not found
```

При этом sitemap сайта был доступен. Поэтому следующий вопрос стал более конкретным: **почему Hugo не создавал ожидаемый `robots.txt`?**

### 1. Проверка конфигурации Hugo

Сначала был проверен файл `hugo.toml`.

В конфигурации присутствовало:

```toml
enableRobotsTXT = true
```

То есть Hugo был явно настроен на создание файла `robots.txt`.

### 2. Проверка явного robots-шаблона

Следующим шагом был поиск шаблона, который мог определять содержимое этого файла.

Были проверены:

```text
layouts/robots.txt
themes/hugo-book/layouts/robots.txt
static/robots.txt
```

Ни одного из этих файлов не существовало.

На этом этапе конфигурация показывала, что Hugo должен создавать `robots.txt`, но явного шаблона `robots.txt` не было ни в проекте, ни в ожидаемом расположении внутри темы.

### 3. Сборка сайта

Затем сайт был собран локально:

```bash
hugo
```

В результате появился:

```text
public/robots.txt
```

Это было важное открытие — но **ещё не успешный результат**.

Размер сгенерированного файла составлял примерно **34 КБ**.

Вместо небольшого набора robots-директив он содержал:

```text
Pivtorak.Studio
- ...
```

а затем длинный список страниц сайта.

Таким образом, расследование перешло от вопроса:

```text
Почему robots.txt отсутствует?
```

к вопросу:

```text
Почему Hugo генерирует это содержимое как robots.txt?
```

### 4. Проверка поиска шаблона

После этого расследование перешло непосредственно к теме Hugo.

Был найден важный файл:

```text
themes/hugo-book/layouts/all.txt
```

Именно этот неожиданный шаблон оказался связан с полученным результатом.

Выстроилась следующая техническая цепочка:

```text
enableRobotsTXT = true
        ↓
Hugo генерирует robots output
        ↓
output type: text/plain
        ↓
поиск шаблона
        ↓
явного шаблона robots.txt нет
        ↓
выбирается all.txt
        ↓
неожиданное содержимое становится /robots.txt
```

Важно, что сгенерированный файл не был случайным или повреждённым. Hugo действительно создавал output-файл — но использовал для этой задачи неправильный шаблон.

### 5. Остановка перед deployment

На этом этапе сгенерированный `public/robots.txt` **не был закоммичен и не был опубликован**.

Файл существовал.

Сборка завершилась успешно.

Но содержимое было неправильным.

Именно это различие стало главным результатом проверки:

> **Успешная сборка ещё не доказывает, что сгенерированный файл правильный.**

Поэтому необходимо было проверить source, затем сгенерированный результат и только после этого — live-сайт.

## Что мы обнаружили

Расследование показало, что проблема заключалась не просто в отсутствии `robots.txt`.

Более важным оказалось другое:

> **Hugo создавал файл по ожидаемому пути — но содержимое генерировалось из неправильного шаблона.**

|Проверка|Ожидалось|Обнаружено|Доказательство|
|---|---|---|---|
|`/robots.txt` на сайте|корректный файл robots|первоначально `404 File not found`|проверка live URL|
|Конфигурация Hugo|`enableRobotsTXT = true`|подтверждено|`hugo.toml`|
|Явный шаблон robots|`layouts/robots.txt` или другой предназначенный для него источник|отсутствовал|проверка исходников|
|Локальная сборка|`public/robots.txt` с robots-директивами|файл создан, но размером около 34 KB|сборка `hugo`|
|Содержимое созданного файла|`User-agent`, `Allow`, `Sitemap` и т. д.|`Pivtorak.Studio` + длинный список страниц/URL|созданный `public/robots.txt`|
|Поиск шаблона|специальный шаблон для robots|был задействован `themes/hugo-book/layouts/all.txt`|проверка темы|

### Неожиданный шаблон

Проблема привела к файлу:

`themes/hugo-book/layouts/all.txt`

Логика оказалась следующей:

```text
hugo.toml
enableRobotsTXT = true
        │
        ▼
Генерация robots-вывода Hugo
        │
        ▼
text/plain
        │
        ▼
Поиск шаблона
        │
        ├── нет явного layouts/robots.txt
        │
        ▼
themes/hugo-book/layouts/all.txt
        │
        ▼
Сгенерированный файл около 34 KB
        │
        ▼
Неправильное содержимое /robots.txt
```

Важно различать две вещи:

**Сборка была успешной с точки зрения Hugo.  
Но результат был неуспешным с точки зрения назначения файла.**

### Что позволили установить доказательства

1. В `hugo.toml` присутствовал `enableRobotsTXT = true`.  
2. Явного шаблона `robots.txt` в проверенных местах не было.  
3. Hugo создавал `public/robots.txt`.  
4. Размер созданного файла составлял около 34 KB.  
5. Вместо ожидаемых robots-директив файл содержал текст, связанный с сайтом, и длинный список страниц/URL.  
6. В ходе расследования был обнаружен неожиданный шаблон `themes/hugo-book/layouts/all.txt`, участвовавший в формировании этого вывода.  
7. Неправильный файл был обнаружен **до коммита и деплоя**.  

Цепочка причины:

```text
Robots-вывод Hugo
        ↓
поиск шаблона
        ↓
универсальный all.txt
        ↓
неожиданное содержимое
        ↓
неправильный robots.txt
```

### Что мы не устанавливали

В рамках этого расследования не измерялось конкретное влияние проблемы на:

- crawl budget;  
- индексацию;  
- позиции в поисковой выдаче;  
- органический трафик.  

Поэтому такие последствия нельзя представлять как измеренный результат этого инцидента.

### Практический вывод

Файл может существовать по правильному URL, успешно создаваться во время сборки и всё равно содержать **не тот вывод, который требуется для его функции**.

Поэтому проверки существования файла недостаточно.

Нужно проверять цепочку:

**Source → Build → Live**

и смотреть не только на наличие файла, но и на его фактическое содержимое.

## Исправление

Исправление было намеренно простым: вместо того чтобы полагаться на механизм поиска шаблонов Hugo при определении содержимого `/robots.txt`, мы создали для этого файла явный шаблон.

### 1. Создание явного шаблона robots

Был создан новый файл:

```text
layouts/robots.txt
```

со следующим содержимым:

```text
User-agent: *
Allow: /

Sitemap: {{ "sitemap.xml" | absURL }}
```

Это делает ожидаемый результат явным.

- `User-agent: *` применяет правила ко всем поисковым роботам.  
- `Allow: /` разрешает crawling сайта.  
- `Sitemap:` указывает абсолютный URL сгенерированного sitemap.  

Здесь важно не количество директив. Главное — **взять под контроль шаблон, который генерирует `/robots.txt`**.

### 2. Почему это решает проблему

До исправления процесс генерации выглядел так:

```text
enableRobotsTXT = true
        │
        ▼
Robots output Hugo
        │
        ▼
Поиск шаблона
        │
        ▼
themes/hugo-book/layouts/all.txt
        │
        ▼
Неправильное содержимое
        │
        ▼
/robots.txt
```

После исправления:

```text
enableRobotsTXT = true
        │
        ▼
Robots output Hugo
        │
        ▼
layouts/robots.txt
        │
        ▼
Явно заданные robots-директивы
        │
        ▼
/robots.txt
```

Ключевым изменением стало добавление:

```text
layouts/robots.txt
```

Это устраняет неоднозначность, из-за которой для данного output мог использоваться универсальный шаблон `all.txt`.

### 3. Полное содержимое шаблона

Для воспроизводимости решения полный файл выглядит так:

```text
User-agent: *
Allow: /

Sitemap: {{ "sitemap.xml" | absURL }}
```

URL sitemap генерируется динамически с помощью функции `absURL` Hugo, а не прописывается непосредственно в шаблоне.

### 4. Важное правило

Исправление **не было сразу опубликовано**.

Сначала новый шаблон проверили локально:

```text
Source → Build
```

И только после того, как сгенерированный `public/robots.txt` содержал ожидаемые robots-директивы, результат был переведён на следующий этап:

```text
Build → Live
```

Это сохраняет главный урок данного инцидента:

> **Не публикуйте исправление только потому, что исходный код выглядит правильно. Сначала проверьте сгенерированный результат.**

## Проверка

Исправление было проверено на трёх уровнях:

**Source → Build → Live**

Каждый уровень отвечал на отдельный вопрос:

|Уровень|Вопрос|Результат|
|---|---|---|
|**Source**|Присутствует ли нужный шаблон robots?|Да — создан `layouts/robots.txt` с ожидаемыми директивами.|
|**Build**|Создаёт ли Hugo правильный файл?|Да — сгенерированный `public/robots.txt` содержал ожидаемые robots-директивы.|
|**Live**|Попал ли исправленный файл на production-сайт?|Да — live `/robots.txt` возвращал исправленное содержимое.|

### 1. Source

Сначала был проверен исходный код.

Новый файл:

```text
layouts/robots.txt
```

содержал:

```text
User-agent: *
Allow: /

Sitemap: {{ "sitemap.xml" | absURL }}
```

На этом этапе вопрос был простым:

> **Присутствует ли нужный исходный шаблон в правильном месте и содержит ли он правильные инструкции?**

Да.

Но одного исходного кода было недостаточно для подтверждения исправления.

### 2. Build

Затем сайт был собран локально командой:

```bash
hugo
```

После этого непосредственно проверили созданный файл:

```text
public/robots.txt
```

Главным изменением стало то, что сгенерированный output теперь содержал robots-директивы, а не прежний список страниц сайта.

Ожидаемое содержимое после генерации:

```text
User-agent: *
Allow: /

Sitemap: https://pivtorak.studio/sitemap.xml
```

Это подтвердило, что исходный шаблон действительно создаёт нужный результат.

Таким образом, переход от:

**Source → Build**

был сделан только после непосредственной проверки сгенерированного файла.

### 3. Live

Только после того, как локальная сборка дала правильный результат, изменение было опубликовано.

После этого был проверен production URL:

```text
https://pivtorak.studio/robots.txt
```

Финальный ответ live-сайта:

```text
User-agent: *
Allow: /

Sitemap: https://pivtorak.studio/sitemap.xml
```

Это подтвердило, что исправленный файл действительно попал на production-сайт.

### 4. Доказательство deployment

Публикацию также можно проследить по истории проекта:

```text
Commit: 8c98ac0a
GitHub Actions run: #2739
Статус: deployment успешно завершён
```

Это дополнительно связывает проверенное изменение в исходном коде с результатом на live-сайте.

### Цепочка проверки

```text
SOURCE
layouts/robots.txt
        │
        ▼
BUILD
public/robots.txt
        │
        ▼
LIVE
https://pivtorak.studio/robots.txt
        │
        ▼
Корректные robots-директивы
```

### Что подтверждает эта проверка

Проверка устанавливает, что:

1. нужный исходный шаблон существует;  
2. Hugo создаёт ожидаемый `robots.txt`;  
3. сгенерированный файл был опубликован;  
4. live URL возвращает исправленное содержимое.  

При этом сама по себе эта проверка **не устанавливает** последующих изменений в crawling, индексации, позициях в поисковой выдаче или органическом трафике.

Для этого потребовались бы отдельные измерения во времени.

> **Техническое исправление считается проверенным, когда исходный код создаёт ожидаемый результат при сборке — и этот результат подтверждён на live-сайте.**

## Итоговый вывод

Проблема с `robots.txt` не всегда означает, что файл отсутствует.

Иногда файл существует.  
Иногда Hugo успешно создаёт его.  
И всё же это может быть неправильный файл.

Главный урок этого инцидента прост:

> **Не проверяйте только наличие `/robots.txt`. Проверьте, что его создало, что именно построил Hugo и что на самом деле отдаёт live-сайт.**

Надёжная последовательность:

**Source → Build → Live**
